# Helpdesk AI 客服智能体 —— 用户故事与验收标准

> 依据项目 README 梳理的核心能力（FAQ 问答、工单生成、投诉处理、多轮记忆、服务反馈、快捷提问、会话管理、响应式布局）编写，遵循 INVEST 原则，验收标准采用 Gherkin 语法。

---

## 故事 1：知识库 FAQ 问答

**用户故事：**
角色：作为一名使用客服系统的终端用户，
功能：我想要就常见问题（如服务时间、退换货政策等）向智能客服提问并获得基于知识库的准确回答，
价值：以便能够无需等待人工客服即可快速自助解决问题。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：提问命中知识库中的已有答案
Given 用户打开 Web 聊天界面并已填写 session_id 与 user_id
When 用户发送消息"你们的服务时间是什么？"
Then 系统应识别意图为 "FAQ"
And 消息气泡应返回包含来源引用标记（如"【1】"）的准确答案
And 消息气泡应显示 "FAQ" 意图徽章

场景：提问未命中知识库
Given 用户在聊天界面
When 用户发送消息"发票要如何开具？"（知识库中无对应内容）
Then 系统应返回意图为 "FAQ" 的降级回复，明确说明检索结果中没有相关信息
And 回复内容应包含转人工或联系支持团队的建议（如邮箱、电话）
And 系统应在 3 秒内完成响应

## 故事 2：自动创建工单

**用户故事：**
角色：作为一名遇到产品或账号问题的用户，
功能：我想要在对话中直接描述问题并由智能客服自动创建工单，
价值：以便能够无需额外填写表单即可快速获得后续人工跟进。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：通过自然语言触发工单创建
Given 用户在聊天界面且已提供 session_id 与 user_id
When 用户发送消息"我无法登录账号，请帮我创建一个工单"
Then 系统应识别意图为 "TICKET"
And 系统应调用 create_or_update_ticket 工具生成唯一工单号
And 返回消息中应包含工单号与当前状态（如 "open"）
And 消息气泡应高亮展示该工单号

场景：在同一会话中补充信息更新已创建的工单
Given 用户已在当前 session_id 下成功创建工单
When 用户在同一会话中补充描述"刚才的问题是在 iOS 客户端上出现的"
Then 系统应将补充信息更新到同一工单，而不是新建一个工单
And 返回的 ticket_id 应与此前返回的一致

## 故事 3：投诉意图识别与处理

**用户故事：**
角色：作为一名对服务或产品不满的用户，
功能：我想要向智能客服表达投诉内容并被准确识别为投诉类诉求，
价值：以便能够得到区别于普通咨询的重视和响应，情绪被妥善安抚。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：识别并标记投诉意图
Given 用户在聊天界面
When 用户发送带有负面情绪的消息，如"你们的客服态度太差了，我要投诉"
Then 系统应识别意图为 "COMPLAINT"
And 消息气泡应显示"投诉"意图徽章
And 系统回复应包含安抚性语言，并说明后续处理方式（如是否已同步生成工单）

## 故事 4：多轮会话记忆

**用户故事：**
角色：作为一名与客服智能体进行连续多轮对话的用户，
功能：我想要智能客服记住我在当前会话中之前提到的信息，
价值：以便能够不必重复描述背景，获得连贯的对话体验。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：智能体结合上文信息回答后续问题
Given 用户已在 session_id "s5" 中告知"我的账号是 user_123"
When 用户在同一 session_id 下追问"帮我查一下我的工单进度"
Then 系统应结合此前提到的账号信息作答，不要求用户重新提供
And 返回结果的 session_id 应与请求一致，保持上下文关联

场景：不同 session_id 之间上下文互不干扰
Given 用户在 session_id "s5" 中提供过账号信息
When 用户切换到新的 session_id "s6" 并提出相同问题
Then 系统不应沿用 "s5" 中的历史上下文
And 系统应提示用户补充必要信息，视为全新对话处理

## 故事 5：服务满意度反馈

**用户故事：**
角色：作为一名刚获得智能客服回复的用户，
功能：我想要对本次回复进行星级评分并填写评论，
价值：以便能够表达我的满意度，帮助企业持续改进客服质量。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：提交有效的评分与评论
Given 用户已收到智能客服的一条回复
When 用户在反馈表单中选择 5 星评分并填写评论"回复很及时，谢谢！"
And 用户点击提交
Then 系统应调用 /feedback 接口，携带 session_id、score、comment
And 系统应返回 {"ok": true}
And 界面应提示"反馈已成功提交"

场景：未选择星级时提交反馈
Given 用户打开反馈表单
When 用户未选择任何星级评分直接点击提交
Then 系统应阻止提交并提示"请先选择评分"
And 系统不应向 /feedback 接口发起请求

## 故事 6：快捷提问

**用户故事：**
角色：作为一名刚进入客服对话、不确定该问什么问题的用户，
功能：我想要通过点击内置的常见问题按钮快速发起提问，
价值：以便能够降低输入成本，更快获得常见问题的答案。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：点击快捷问题按钮发起提问
Given 用户打开 Web 聊天界面的输入区
When 用户点击某条内置快捷问题（如"服务时间是什么？"）
Then 该问题文本应自动作为用户消息发送
And 系统应按正常 /chat 流程返回对应意图徽章与答案

---

## 故事 7：会话管理

**用户故事：**
角色：作为一名需要管理多个客服会话的用户，
功能：我想要在侧边栏查看并编辑当前的会话 ID 与用户 ID，并能一键清空对话，
价值：以便能够灵活切换、隔离不同会话场景，并在需要时重新开始对话。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：编辑会话 ID 以开始新会话
Given 用户在侧边栏看到当前 session_id 为 "s1"
When 用户将 session_id 修改为 "s9" 并发送新消息
Then 后续请求应使用 "s9" 作为 session_id
And 聊天区不应显示 "s1" 会话下的历史消息

场景：清空当前对话
Given 聊天区已存在多条历史消息
When 用户点击"清空对话"按钮
Then 聊天区的消息列表应被清空
And 不应影响后端已存储的历史工单或反馈数据

---

## 故事 8：响应式布局

**用户故事：**
角色：作为一名使用手机访问客服系统的用户，
功能：我想要在移动端浏览器中获得与桌面端一致的可用聊天体验，
价值：以便能够随时随地通过手机获得客服支持。

**验收标准（Acceptance Criteria - Gherkin 语法）：**

场景：移动端访问聊天界面
Given 用户使用手机浏览器（视口宽度 ≤ 480px）访问 Web 聊天界面
When 页面加载完成
Then 侧边栏、聊天区、输入框应自适应调整为移动端布局（如侧边栏可收起）
And 用户应能正常发送消息并查看带意图徽章的回复气泡

## INVEST 自检说明

- **Independent**：每个故事对应一个独立接口或 UI 模块（/chat 不同意图分支、/feedback、侧边栏组件），可独立开发与发布。
- **Negotiable**：具体 UI 呈现方式（如徽章颜色、按钮位置）留给设计与开发协商，故事只约束行为与价值。
- **Valuable**：每条均直接对应用户或企业可感知的价值（自助解决问题、减少人工介入、改进服务质量等）。
- **Estimable**：功能边界清晰（对应 README 中已有的具体接口/组件），便于估算工作量。
- **Small**：每个故事聚焦单一场景（FAQ、工单、投诉、记忆、反馈、快捷提问、会话管理、响应式），可在一个迭代内完成。
- **Testable**：每条故事均配有可执行的 Gherkin 场景，包含正向与异常路径，可直接转化为自动化测试用例。
